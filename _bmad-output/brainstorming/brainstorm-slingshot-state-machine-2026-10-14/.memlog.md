- (technique) started Morphological Analysis
- (idea by user) Axis G (input): separate Input System Action Map per active state; each state enables its relevant action maps and disables the rest on enter/exit. Mobile game, tap is primary input.
- (decision by user) Input map switching is decentralized: each state, on enter, enables its own relevant Action Map and disables the rest.
- (decision by user) Drag->power/angle math lives inside the Charge state component itself (self-contained), not a shared helper (for now).
- (decision by user) Transitions: a state calls machine.GoTo(nextState) on a central manager to pass control.
- (decision by user) REVISED routing: each state holds serialized GameplayState (abstract) fields for its possible next states (e.g. Shot has onStopState + onCrashState; single-exit states have one field). States are components dragged into each other's serialized fields; each state's own logic picks which next state to invoke. Flow graph is thus visible/editable in the inspector.
- (decision by user) Run-loop delegated to the character: states hold a reference to the character prefab (self-animated, own logic, throws events). State subscribes to the character's events; the character manages its own state and owns its Run()/movement logic. State machine = orchestrator reacting to character events, not a physics driver.
- (idea by user) Character event contract: SlowedDown (hit a slowing obstacle), Crashed (hit a stopping obstacle), MomentumEnded(distance) (momentum ran out, reports distance travelled).
- (insight by coach) Not every character event is a transition: SlowedDown is pure feedback (camera shake / near-miss juice) handled in-state, no GoTo. Only Crashed and MomentumEnded route. Shows the orchestrator can react to events presentationally without changing state.
- (decision by user) Separate EvaluateDistance state (no visuals, a decision node): reads TraveledDistance from the Character (holds a Character reference) and routes to onNewRecordState vs onTryEndedState.
- (insight by coach) The Character is becoming the shared context/blackboard (Axis E): many states reference it (Shot commands it, Evaluate reads TraveledDistance). Worth separating character-owned per-run data (TraveledDistance, resets each launch) from persistent session data (best distance, survives respawn) which should NOT live on the character.
- (decision by user) ScoreManager holds the level's best result for the current session; EvaluateDistance compares against it. Persistence across sessions is out of scope (future service will init ScoreManager). Brainstorm scope = the state machine only.
- (technique) started Assumption Reversal
- (decision by user) Reversal resolved via COMPOSITION, not concurrency: keep one active state per machine (simpler), but allow separate/nested state machines that can be referenced from states of this machine. A state can drive a sub-machine (e.g. rewards flow), avoiding multiple-active-states complexity.
- (insight) SYNTHESIS: The machine is a thin ORCHESTRATION layer that never touches physics - it only COMMANDS (character.Launch) and REACTS (events). Every state reduces to: configure presentation on Enter, react to one event, GoTo. One pattern (command -> subscribe -> react) recurs everywhere: state<->character, state<->sub-machine (future), state<->input-map. SlowedDown as a non-transition event proves flow is cleanly separated from feedback - this keeps state count from exploding as juice is added. EvaluateDistance (visual-less decision node) is the reusable template for adding any future branch cheaply. Flexibility comes from COMPOSITION (nested machines) not concurrency, and from the inspector-visible flow graph (serialized next-state refs). Build-ready.
- (decision by user) Open points resolved: (1) Charge reads drag in its own gated Update(); (2) NewRecord goes straight back to the initial Waiting state.
- (decision by user) Cinemachine: use ONE shared CinemachineCamera with Orbital Follow for the Wait<->Aim transition; animate the orbit horizontal angle (+ height/distance) between presets to get a true circular sweep around the character, instead of swapping cameras.
- (decision by user) States use async transitions: instead of fire-and-forget, a state AWAITS orbitalCameraRig.AnimateToAsync() (and similar). Implies async state lifecycle (e.g. async Enter) so transitions sequence properly (enable input only after the camera sweep completes).
