- (direction by user) Character moves through the world (not a world-scrolling treadmill); no assumption-reversal to a parked character.
- (direction by user) Momentum/movement is script-driven and kinematic, NOT Unity-physics-based — must be fully parametrizable later; no realistic bouncing/collision response.
- (technique) started Morphological Analysis
- (decision by user) RunningState receives two launch params from Charge/Shot: charge strength (seeds initial forward momentum/speed) and aim direction (seeds initial heading). Matches existing Character.Launch(power, direction) contract.
- (idea by user) Axis A (forward driver): use CharacterController.Move() — kinematic, collide-and-slide handles track edges, fed a per-frame velocity the script owns.
- (idea by user) Axis B (steering): target-X lerp — input sets a target lateral offset within the track; character eases toward it each frame (smooth/banked, predictable).
- (idea by user) Axis C (boundary): left/right boundary transforms placed by the level author define the lateral extent; target-X is clamped between them before the lerp (CharacterController collide-and-slide is the backstop).
- (idea by user) Axis D (distance): total path length — accumulate the magnitude of each full CharacterController.Move delta (forward + lateral). Steering/weaving counts toward distance.
- (idea by user) Axis E (momentum profile): AnimationCurve authored in the inspector drives forward speed over the run (launch->stop); fully tunable without code. MomentumEnded fires at the curve's end / low-speed cutoff.
- (idea by user) Axis E refinement: charge strength scales BOTH peak speed and duration — via a mapping (e.g. chargeStrength->peakSpeed curve + chargeStrength->duration curve) feeding the speed AnimationCurve. Harder pull = faster AND longer run.
- (idea by user) Axis F (level layout): prefab per level — each level is a prefab holding track mesh, left/right boundary transforms, spawn point (and later obstacles). Swap the prefab to swap levels; fully visual in the editor.
- (insight by coach) Morphological grid complete — coherent design: CharacterController.Move kinematic driver + target-X lerp steering clamped to boundary transforms + total-path distance + charge-scaled AnimationCurve momentum (peak+duration) + prefab-per-level.
- (decision by user) Run ends two ways: (a) momentum decays to zero — some obstacles SLOW the character (bleed momentum) along the way; (b) CRASH into a deadly obstacle. Maps to Character SlowedDown / Crashed / MomentumEnded.
- (insight by coach) Tension (TRIZ-ish): if speed = curve.Evaluate(t)*peak, a slowing obstacle can't just subtract — next frame the pure f(t) curve overrides the slowdown. The momentum model must let obstacles perturb the curve, so curve-as-pure-function-of-time breaks.
- (idea by user) Momentum model = reserve/fuel: AnimationCurve sets how fast fuel drains; hitting a slowing obstacle deducts fuel directly; run ends (MomentumEnded) when fuel reaches zero.
- (insight by coach) Elegant consequence: charge strength seeds INITIAL FUEL, which alone scales both peak speed and duration (more fuel = start faster + drain longer) — replaces the earlier two-curve peak/duration mapping with one value.
- (idea by user) Fuel->speed: speed = fuel * k (directly proportional to remaining fuel). Drain rate = curve.Evaluate(fuel/initialFuel) — a function of fuel remaining (self-referential sputter-to-stop).
- (insight by coach) Termination caveat: since drain = curve(fuelFraction), the drain curve must stay > 0 across the whole range (or add a min-drain floor), else fuel stalls at a plateau and MomentumEnded never fires.
- (question by user) Run camera: should RunningState use the SAME CinemachineCamera (orbital rig) or an ADDITIONAL dedicated chase camera? Must blend smoothly.
- (direction by user) Loop-back requirement: when run ends + terminal state finishes, machine resets to Waiting; character must already be standing at the initial position with the camera framing him, and the whole reset must feel smooth.
- (question by user) Open thread: how to TEST RunningState without Charge implemented / without real momentum+direction params being passed in.
- (idea by user) Run camera: ADDITIONAL dedicated chase CinemachineCamera (e.g. Third Person Follow), Prioritize()'d by RunningState on enter; Waiting's camera re-prioritized on reset; CinemachineBrain blends automatically — matches existing Prioritize() pattern.
- (idea by user) Smooth reset: hide the snap-back behind the UI fade — terminal state fades out, re-prioritize Waiting camera + reset character to spawn behind black, fade in with Waiting framing the origin. No cross-level camera swoop.
- (insight by coach) CharacterController reset caveat: can't just write transform.position while it's enabled (it fights the move). Pattern: cc.enabled=false; transform.position/rotation=spawn; cc.enabled=true; also reset fuel/distance/steer-target. Do it during the fade.
- (decision by user) Test harness = a stub/debug ChargeState on the state machine GameObject with editor-exposed power + direction fields. In Aim, a tap (not the Back button) enters this Charge, which immediately Configures Shot with the preconfigured serialized values and transitions — real Aim->Charge->Shot->Running path, drag math replaced by serialized fields. Lets RunningState be built/tested before real drag exists.
- (decision by coach) MoSCoW — MUST (first RunningState slice): RunningState w/ CharacterController.Move kinematic driver; fuel momentum (speed=fuel*k, drain curve over fuel-fraction, charge->initialFuel); target-X lerp steering clamped to L/R boundary transforms; total-path distance; MomentumEnded at fuel=0; additional chase CinemachineCamera prioritized on enter; smooth reset behind fade (cc.enabled toggle + re-prioritize Waiting cam); stub ChargeState (serialized power/direction, tap->Shot) as harness; one level prefab (mesh+boundaries+spawn).
- (decision by coach) MoSCoW — SHOULD: obstacle components (slow=fuel penalty via SlowedDown, deadly=Crashed) with trigger-collider detection; PlayMode tests for momentum/boundary/distance math; min-drain floor so drain curve stays >0 (guaranteed termination).
- (decision by coach) MoSCoW — COULD: variable-width tracks (series of boundary pairs) + multiple level prefabs; steering-feel tuning while slowed. WON'T this time: real drag-based Charge (stub stands in), animations, cross-session persistence, rewards sub-flow.
- (insight) Synthesis: (1) fuel model collapses the Axis-E two-curve peak+duration mapping into one 'initial fuel' value seeded by charge. (2) target-X clamp = steering + boundary + collision safety in one mechanism. (3) existing UiScreenView fade already covers the reset teleport — no new system. (4) KEY integration: per the existing spec, the Character (a concrete subclass of the stub) owns the movement model; 'RunningState' == the existing ShotState (flight state commands Launch + reacts), NOT a state that drives physics. Unity components mapped per concern (CharacterController.Move, AnimationCurve, Input System, CinemachineCamera+ThirdPersonFollow+Brain, boundary transforms, trigger colliders, prefab-per-level, UniTask).
