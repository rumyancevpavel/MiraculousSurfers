- (note) Derived from brainstorm memlog (_bmad-output/brainstorming/brainstorm-slingshot-state-machine-2026-10-14/.memlog.md) and scaffolded code in Assets/MiraculusSurfers/Scripts/Gameplay (namespace MiraculousSurfers.Gameplay).
- (capability) CAP-1 Start a run: from the initial Waiting state the camera frames the character and 'Tap to begin' shows; a tap advances to Aim. Success: before tap no launch input is accepted; tapping enters Aim.
- (capability) CAP-2 Aim or back out: in the behind-the-character Aim view the player can return to Waiting or begin a drag to charge. Success: Back -> Waiting; starting a drag -> Charge.
- (capability) CAP-3 Charge and release: dragging sets power (pull distance) and direction (left/right); easing off reduces tension; releasing past a threshold launches, below it returns to Aim. Success: release past threshold launches with power/direction matching the drag; below threshold returns to Aim with no launch.
- (capability) CAP-4 Flight and outcome routing: after launch the character slides under its own physics; the machine reacts to character events and routes, with no return to pre-shot states. Success: Crashed->Crash, MomentumEnded->evaluation, SlowedDown->feedback only (no transition); no transition back to Charge/Aim/Waiting during flight.
- (capability) CAP-5 Evaluate against session best: when momentum ends, travelled distance is compared to the session best to choose new-record vs ordinary end. Success: distance > best routes to New Record and updates best; otherwise Try Ended.
- (capability) CAP-6 Resolve and loop: New Record celebrates + marks the record on the level map then returns to Waiting; Try Ended returns to Waiting; Crash plays death anim then returns to Waiting. Success: each terminal state completes its presentation and the machine returns to the initial Waiting state.
- (capability) CAP-7 Editor-configured, extensible states: each state is a separate component whose dependencies are wired in the inspector; states/variants can be added or swapped without changing other states. Success: swapping a next-state ref or replacing a state with a variant changes the flow with zero code change to other states; the flow graph is readable via serialized references.
- (constraint) One active state at a time per machine; parallel behavior is achieved via nested/referenced sub-machines (composition), never concurrent states.
- (constraint) Transitions routed by serialized next-state references on each state (inspector-visible flow graph); a state calls machine.GoTo(next) and its own logic picks which exit (Shot: onCrash/onStop; single-exit states: one ref).
- (constraint) The machine never drives physics: the character is a self-driving actor owning movement/animation and emitting SlowedDown, Crashed, MomentumEnded(distance); the machine only commands (Launch) and reacts.
- (constraint) Input is decentralized per state via Unity Input System Action Maps: each state enables its own map and disables the rest on enter/exit. Mobile-first; tap and drag are primary.
- (constraint) Transitions are async via UniTask: a state awaits presentation (e.g. the camera sweep) before enabling input. Coroutines are forbidden (UniTask only) per project convention.
- (constraint) Camera uses Cinemachine: one shared CinemachineCamera with Orbital Follow, animated between orbit presets (not camera-swapping) for the Wait<->Aim circular sweep around the character.
- (constraint) SlowedDown is feedback-only and must never cause a state transition.
- (constraint) Session best lives in a ScoreManager (not on the character); per-run TraveledDistance lives on the character and resets each launch.
- (decision) Non-goal: cross-session persistence of best distance (a future service will init ScoreManager).
- (decision) Non-goal: slingshot visuals / art (explicitly deferred).
- (decision) Non-goal: building the nested rewards sub-flow/sub-machines now (architecture allows referencing them; implementing them is later).
- (decision) Non-goal: the character's internal movement/physics/animation implementation (owned by the character; a contract stub here).
- (assumption) The character prefab exists (or will) as a self-driving actor matching the event + Launch(power,direction) contract; currently a stub (Character.cs).
- (assumption) Charge computes power/direction then configures Shot, which subscribes-before-launch; i.e. Shot owns Launch, Charge owns the drag math (as implemented in the scaffold).
- (question) How does horizontal drag map to world launch direction (ground-plane projection, sensitivity, clamps)? Left for tuning.
- (question) Should terminal-state completion (NewRecord celebration, Crash death anim) be driven by animation events/signals rather than the scaffold's placeholder fixed delays?
