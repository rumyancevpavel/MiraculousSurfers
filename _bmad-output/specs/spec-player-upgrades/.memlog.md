- (note) Distilled from the Player Upgrades architecture spine (architecture-player-upgrades-2026-10-15/ARCHITECTURE-SPINE.md + its memlog). Adopts that spine and ../spec-save-system/SPEC.md as companions; cites AD-1..AD-9. Implementation to follow.
- (capability) CAP-1 Incremental upgrade of a param: the player buys the next upgrade step for a param, raising its gameplay multiplier by one index. success: after a successful TryUpgrade, the param index increments by 1 and GetValue(param) returns the config Value at the new index.
- (capability) CAP-2 Affordability/max gating: an upgrade is purchasable only when affordable and not maxed. success: TryUpgrade with Coins < next price, or at max (HasNext false), returns Ok with Applied=false, charges nothing, and leaves state unchanged; CanUpgrade(param) reflects the same.
- (capability) CAP-3 Charge on purchase: a successful purchase deducts exactly the next step price from the wallet. success: coins decrease by Price(param, index+1) after a successful TryUpgrade, via IWalletService.TrySpend.
- (capability) CAP-4 Durable upgrade state: upgrade indices persist across app restarts through the save system. success: buy an upgrade, restart, the saved index and its derived value are restored.
- (capability) CAP-5 Config-driven tuning: per-param steps, values, prices, and max level come from the game-configuration system (ScriptableObject). success: editing the SO ladder changes the reported Value/Price/StepCount with no code change, and HasNext is false at max.
- (capability) CAP-6 Derived gameplay values: gameplay reads a param's current multiplier through IUpgradeService.GetValue, reflecting the live upgrade index. success: a gameplay consumer obtains e.g. LaunchPower via GetValue and it equals config.Value(param, currentIndex).
- (capability) CAP-7 Change-notification seam: consumers (the future HomeScreenUI) are notified when a param upgrades. success: a subscriber to IUpgradeService.Changed receives the UpgradeParam after a successful purchase, including when persisted=false.
- (capability) CAP-8 Optimistic persistence outcome (D1): a purchase reports whether it persisted. success: with a forced save failure, TryUpgrade returns Ok with Applied=true and Persisted=false, and the in-memory index is still raised.
- (constraint) Persisted state = int index per param (AD-2); value derived via IGameConfigurationSystem.Value, never stored; index clamped to [0,StepCount] on load. This REVISES already-shipped PlayerUpgradesData (floats->int indices) and the save-system spec CAP-8 (defaults all 1.0 -> indices default 0).
- (constraint) Single stateful owner (AD-1): UpgradeService alone holds live PlayerUpgradesData; gameplay and UI read only through IUpgradeService. Enum-keyed addressing (UpgradeParam); GetNextCost returns 0 at max; Changed fires on any in-memory apply regardless of Persisted (AD-4).
- (constraint) Fallible ops reuse MiraculousSurfers.Core.Result (AD-5): TryUpgrade returns IResult<UpgradePurchase{bool Applied;bool Persisted;int NewIndex;float NewValue}>; Ok for expected outcomes (unaffordable/maxed/applied-but-not-persisted), Fail only for an unexpected throw; pure queries return raw types.
- (constraint) Tuning only via IGameConfigurationSystem (AD-3), ScriptableObject-backed now (LocalGameConfigurationSystem reads a GameConfiguration SO): index-addressed StepCount/Value/Price/HasNext; index 0 = base; upgrade i->i+1 costs Price(i+1); no hardcoded steps/prices.
- (constraint) Wallet is single-currency int coins behind IWalletService{int Coins; bool TrySpend(int)} (AD-6), mocked non-persistent in-memory now; purchase is optimistic D1 (AD-7): charge->bump index->persist; on save fail keep in-memory and report Persisted=false; no refund/rollback while the wallet is non-persistent.
- (constraint) DI: all four services (save, config, wallet, upgrade) register as Singletons in the single existing GameplayLifetimeScope (AD-8); UpgradeService loads on VContainer IAsyncStartable.StartAsync, falling back to CreateDefault on load failure (AD-9).
- (constraint) Inherited (binding): save-system invariants — stateless S1, Newtonsoft, key-suffix versioning with no migration, VContainer; CLAUDE.md conventions — no comments, var, underscore privates, UniTask not coroutines, int coins/prices, code under Assets/MiraculousSurfers/.
- (decision) Non-goal: HomeScreenUI (out of scope now; the seam is IUpgradeService + the Changed event).
- (decision) Non-goal: a real currency/balance system (wallet is mocked, non-persistent, behind IWalletService).
- (decision) Non-goal: broader game-configuration authoring beyond the upgrade ladders.
- (decision) Non-goal: root-scope promotion / multi-scene support (prototype is single-scope).
- (decision) Non-goal: D1->D2 purchase rollback (refund+revert) while the wallet is non-persistent; and no cross-version save migration (inherited — a format change abandons old saves).
