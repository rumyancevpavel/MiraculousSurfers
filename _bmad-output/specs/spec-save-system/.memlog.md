- (note) Spec is retrospective: distilled from brainstorm memlog brainstorm-data-persistence-system-2026-10-15 AND matches already-implemented code under Assets/MiraculousSurfers/Scripts/Core (Result) and /Data plus Gameplay/GameplayLifetimeScope; generalizes the Tower-of-Colors DataLayer pattern.
- (capability) CAP-1 Durable typed persistence: a caller can save a serializable object and load it back intact across app restarts. success: save an instance, restart, load returns an equal instance (round-trips through Newtonsoft).
- (capability) CAP-2 Non-throwing outcomes: every load/save returns IResult<T> capturing failure as a value, never throwing into gameplay. success: a corrupt/failed read yields Result.Fail (exception captured in Error), not a thrown exception; caller branches on Success.
- (capability) CAP-3 Data-format versioning: each type carries a format version; bumping it makes load read a fresh slot and ignore pre-bump data (no migration). success: after a version bump, load returns defaults and the old blob is untouched/abandoned.
- (capability) CAP-4 First-run safe defaults: when nothing is stored, load returns the type's default instance as a success, not a failure. success: on a fresh install load returns CreateDefault() wrapped Ok.
- (capability) CAP-5 Cheap extensibility: a new persisted type is added by writing a serializable data class plus a small concrete system declaring key/version/default/validation, with no change to the base or backends. success: a new type becomes persistable without editing shared code.
- (capability) CAP-6 Swappable storage backend with a test double that shares the production path: a PlayerPrefs backend (runtime) and an in-memory backend (tests) satisfy the same read/write seam. success: a test drives a concrete system against the in-memory backend and exercises the real serialize+version logic.
- (capability) CAP-7 DI-resolved per-type systems: each type's save system is obtained through the DI container as a closed-generic service and injected into consumers. success: resolving IDataSaveSystem<PlayerUpgradesData> yields PlayerUpgradesSaveSystem (verified in editor).
- (capability) CAP-8 PlayerUpgrades pilot: persists the player's bought upgrade state (LaunchPower, Speed, SteeringResponsiveness, CollectibleValue), every default = 1. success: default load returns all values = 1.0 and a saved set round-trips.
- (constraint) Serialization is Newtonsoft (com.unity.nuget.newtonsoft-json, explicit manifest dep): every persisted type must be Newtonsoft-serializable; this is what makes 'any serializable type' (dictionaries, nested generics, polymorphism, properties, null) actually hold.
- (constraint) Result model is R1 exception-carrying only (no error codes): callers cannot branch on failure CAUSE, so corrupt vs transient read are indistinguishable. Chosen posture F2(a) default-and-overwrite: base returns Fail on corrupt read, caller falls back to CreateDefault(), so a corrupt save can be overwritten with defaults (possible progress loss).
- (constraint) Versioning is a key suffix with NO migration: the format version is part of the storage key, so bumping it abandons pre-bump data and leaves orphaned keys (F3). Accepted pre-launch; post-launch a bump wipes released players' saves.
- (constraint) System is stateless (S1): LoadAsync always re-reads/deserializes, SaveAsync writes what it is handed, nothing is cached between calls. Holding a live in-memory instance and deciding save cadence is the consumer's job, not this system's.
- (constraint) Backend is an inheritance seam, not an injected dependency (for now): the abstract base leaves protected abstract ReadRaw(key)/WriteRaw(key,json); a concrete picks its backend by choosing a base class (PlayerPrefs vs InMemory). Backend swap is a code/base choice, not a DI swap.
- (constraint) Async surface is UniTask<IResult<T>> (no coroutines, per project rule); the PlayerPrefs backend is synchronous under that async surface (UniTask.FromResult).
- (constraint) DI is VContainer: per-type systems are registered as closed generics (Register<IDataSaveSystem<TData>, TConcrete>(Lifetime.Singleton)) in a LifetimeScope; a service is only resolvable/injectable for objects inside that scope.
- (constraint) Mobile IL2CPP/AOT build must preserve Newtonsoft.Json and all persisted data types (F1) via link.xml/[Preserve], or on-device (de)serialize throws; treated as a required build step.
- (constraint) Project coding conventions apply (CLAUDE.md, adopted): no comments in code, private instance fields underscore-prefixed incl. [SerializeField] private, UniTask not coroutines, all code under Assets/MiraculousSurfers/.
- (decision) Non-goal: cross-version data migration (format bump abandons old data by design).
- (decision) Non-goal: encryption / anti-cheat / tamper protection.
- (decision) Non-goal: multiple save slots / profiles.
- (decision) Non-goal: binary/MessagePack serialization (Newtonsoft JSON only).
- (decision) Non-goal: in-memory live-instance caching and save-cadence/service layer (separate future concern on top).
- (decision) Non-goal (future, same seam): extracting an injected IStorageBackend; backup-copy corrupt-recovery F2(c); file/cloud backends.
- (assumption) F1 AOT is likely already covered because com.unity.nuget.newtonsoft-json ships its own link.xml and the data types are referenced directly in code (CreateDefault constructs them, so not stripped); to be confirmed on the first IL2CPP device build.
